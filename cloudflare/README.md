# Cloudflare Worker 3.2-latest-list

`worker.js` — полный исходник для существующего Worker `ps5-telegram-webhook`.

## Установка

1. Открой существующий Worker в Cloudflare и редактор кода.
2. Замени содержимое **активного входного файла `worker.js`** кодом из этого файла. Не создавай второй неиспользуемый entrypoint.
3. Нажми **Deploy**.
4. Открой `https://ps5-telegram-webhook.vov4k95777.workers.dev/health`. При исправной настройке ответ содержит `version: "3.1-review-fixes"`, `db_ok: true`, `ready: true`.
5. Проверь `/list` и `/status` в своём Telegram-боте.

Существующие binding `DB`, таблицы D1 и секреты сохраняются. Миграция базы, создание нового бота, смена токенов и повторный `setWebhook` не требуются.

Обязательные настройки: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `WEBHOOK_SECRET`, `SYNC_SECRET`, привязка D1 `DB`. `GITHUB_READ_TOKEN` и `GITHUB_DISPATCH_TOKEN` остаются опциональными; добавлять их для этого обновления не нужно.

## Изменения

- Проверка завершённости Telegram update и захват обработки выполняются одним SQL-запросом. Запоздавший дубликат не исполняет уже завершённую команду.
- Добавление подписки атомарно проверяет лимит 30 и дубликаты без учёта регистра. Существующая схема базы подходит.
- `/health` проверяет доступность D1. При сбое базы или неполных настройках возвращает HTTP 503 и `ready: false`.
- Запрос GitHub Actions из опциональной команды `/check` ограничен 10 секундами.
- Совместимость `/sync` и `/report` с Python-монитором сохранена.

Это устраняет воспроизведённые гонки, но не делает Telegram и D1 одной транзакцией: при потере ответа после принятого Telegram сообщения редкий повтор всё ещё возможен.

## Версии релизов в /list

- GitHub Actions после очередного сканирования всех доступных репозиториев передаёт в **POST /catalog** (отдельно от /report) метку последней опубликованной версии для каждого успешно проверенного репозитория.
- При выборе учитываются **обычные релизы, Alpha, Beta и Pre-release**. Важен `published_at`, а не порядок или время создания тега. Черновики исключены.
- Доступ к /catalog защищён существующим `SYNC_SECRET`. В D1 используются таблица `settings` и новая строка `monitor_latest_releases`; никакой миграции схемы не требуется.
- Данные объединяются атомарно: предыдущие известные версии сохраняются, если какой-то репозиторий временно не проверился. Более старый отчёт не должен перезаписывать новый.
- Команда `/list` показывает каждый репозиторий и кликабельный тег его последней версии. Если версия пока не получена — «ожидается первая проверка»; если проект не публиковал Releases — «нет опубликованных релизов».
- **Дополнительных запросов GitHub API нет**, поскольку сведения берутся из уже выполненного сканирования. Есть одно небольшое дополнительное обращение GitHub Actions к Cloudflare в конце цикла.
- Перед публикацией этого Worker GitHub Actions может временно получать HTTP 404 от /catalog; это не влияет на сканирование, отправку уведомлений и /status. После Deploy сведения в /list появятся при следующем успешном сканировании.

## Локальная проверка

Нужен Node.js 24. Из корня репозитория:

```sh
node --test cloudflare/worker.test.cjs
```

Тесты используют локальную SQLite и подменённые сетевые вызовы. К действующей D1 и Telegram не обращаются. GitHub workflow проверяет код, но не публикует Worker в Cloudflare.
