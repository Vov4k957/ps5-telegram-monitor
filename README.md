# PS5 GitHub Monitor

Личный Telegram-бот: [@PS5monitorGH_bot](https://t.me/PS5monitorGH_bot).
Отслеживает GitHub Releases, включая Alpha, Beta и Pre-release. Черновики не отправляет.

## Управление в Telegram

- Отправь ссылку `https://github.com/owner/repo`, чтобы подписаться. Текущие релизы запоминаются без рассылки старых уведомлений.
- `/list` — подписки; `/remove` — удаление кнопками в одном сообщении.
- `/translate_on` и `/translate_off` — перевод changelog на русский.
- `/status` — время предыдущей проверки по Москве, источник текущего запуска, последний подтверждённый запуск `schedule` и количество ошибок.
- `/check` — отчёт о проверке при очередном запуске; `/help` — справка.

Команды и кнопки доступны только владельцу в личном чате. Бот опрашивает Telegram при запуске Actions, поэтому ответы приходят с задержкой. Лимит — 30 подписок.

## Расписание и диагностика

Workflow `.github/workflows/ps5-telegram.yml` содержит cron `3-59/5 * * * *`: минуты 03, 08, 13, …, 58 каждого часа. Это желаемый интервал, а не гарантия запуска раз в пять минут.

[GitHub предупреждает о задержках и пропущенных запусках schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule). Workflow должен быть включён и находиться в основной ветке. Изменение cron само по себе не доказывает исправление планировщика.

Проверка: открой [историю Actions](https://github.com/Vov4k957/ps5-telegram-monitor/actions/workflows/ps5-telegram.yml), выбери событие `schedule` и сравни время нескольких последовательных запусков. Успешный `push` или `workflow_dispatch` подтверждает работу скрипта, но не расписания.

При исходной диагностике 28.10.2026 workflow имел статус `active`, основную ветку `main` и корректный cron, но история содержала только два `workflow_dispatch` и один `push`. Точная причина отсутствия schedule не была установлена по доступным данным.

## Бесплатный внешний запуск, если schedule продолжит пропускать проверки

[cron-job.org](https://cron-job.org/en/) может отправлять HTTP-запрос раз в пять минут. Он запускает этот же workflow через `workflow_dispatch`; бот, Telegram Secrets и `release_state.json` остаются в текущем репозитории. Внешний планировщик обходит проблему события `schedule`, но очередь GitHub Actions всё ещё может задержать выполнение.

Это инструкция для подключения; внешний сервис автоматически не подключён.

1. В GitHub открой **Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token**. Выбери **Only select repositories → ps5-telegram-monitor**, право **Actions: Read and write**. Укажи срок действия и сохрани дату: после истечения токен потребуется заменить.
2. Создай аккаунт на cron-job.org и задачу с интервалом пять минут.
3. В дополнительных настройках задачи укажи метод **POST** и URL:

   `https://api.github.com/repos/Vov4k957/ps5-telegram-monitor/actions/workflows/ps5-telegram.yml/dispatches`

4. Добавь заголовки:

   | Заголовок | Значение |
   | --- | --- |
   | `Authorization` | `Bearer ВАШ_GITHUB_TOKEN` |
   | `Accept` | `application/vnd.github+json` |
   | `Content-Type` | `application/json` |
   | `X-GitHub-Api-Version` | `2022-11-28` |

5. Тело запроса: `{"ref":"main"}`. Выполни тестовый запрос, затем проверь новый `workflow_dispatch` в Actions и ответы бота.
6. Включи уведомление cron-job.org об ошибках. После нескольких успешных внешних запусков внутренний cron можно оставить резервным или убрать, чтобы не выполнять лишние проверки.

Токен вводится в защищённые настройки cron-job.org, а не в URL, код или переписку. Сервис получит право запускать Actions только выбранного репозитория. Telegram-токен ему не нужен.

Основание: [возможности cron-job.org](https://cron-job.org/en/faq/) и [GitHub workflow dispatch API](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event).

## Сохранность состояния

**Не удаляй `release_state.json`.** В нём находятся подписки, история release ID, настройки и Telegram offset. В Actions отсутствие или повреждение файла останавливает запуск без создания пустой истории.

Обработанные updates и подтверждённые отправки сохраняются по мере выполнения. Сбой одного репозитория не мешает остальным. ID отмечается доставленным только после успешного ответа Telegram; прежние ID не удаляются при выходе релиза из окна API. Workflow пытается сохранить прогресс даже после ошибки и берёт свежую `main` при запуске. При ошибке Git push сохраняет резервный артефакт на семь дней.

Абсолютное «ровно один раз» между Telegram и Git обеспечить нельзя: если Telegram принял сообщение, но ответ потерялся, либо состояние не удалось записать в Git, при повторе возможен дубль. Обычные повторные проверки и частичная ошибка после подтверждённых отправок не пересылают уже сохранённые релизы.

За одну проверку API получает до 30 последних опубликованных релизов на репозиторий. Долгий простой с большим числом новых релизов может потребовать отдельной сверки истории.

Перевод MyMemory работает без ключа; публичный changelog передаётся этому сервису. Ссылки, версии, код и известные технические термины защищены. При ошибке, исчерпании квоты или времени переводчика отправляется оригинал. Перевод не определяет, поддерживает ли релиз конкретную прошивку PS5.

## Проверки разработчика

`python3 -m unittest -q test_check_releases.py`

Тесты используют временные файлы и подменяют сетевые запросы. Проверяют команды, несколько удалений подряд в одном сообщении, просроченное подтверждение кнопки, защиту владельца, добавление ссылкой, отсутствие старой рассылки, Alpha/Beta, сохранение прогресса после ошибок и резервный оригинал при сбое перевода. Реальные подписки и Telegram при тестах не меняются.
