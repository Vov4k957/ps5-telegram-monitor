# PS5 GitHub Monitor

Личный Telegram-бот: [@PS5monitorGH_bot](https://t.me/PS5monitorGH_bot).
Отслеживает GitHub Releases, включая Alpha, Beta и Pre-release. Черновики не отправляет.

## Управление в Telegram

- Отправь ссылку `https://github.com/owner/repo`, чтобы подписаться. Текущие релизы запоминаются без рассылки старых уведомлений.
- `/list` — подписки с последней опубликованной версией любого типа (включая Alpha, Beta и Pre-release), кликабельным тегом и сроком с момента её выхода; время вычисляется при каждом запросе. `/remove` — удаление кнопками в одном сообщении.
- `/translate_on` и `/translate_off` — перевод changelog на русский.
- `/status` — после обновления Cloudflare Worker показывает последнюю фактическую проверку GitHub Actions (МСК), количество проверенных репозиториев, уведомлений, ошибок и предупреждение о задержке более 5 минут. Данные поступают в D1 после каждого запуска; без новых коммитов.
- `/check` — отчёт о проверке при очередном запуске; `/help` — справка.

Команды и кнопки доступны только владельцу в личном чате. Telegram-команды обрабатываются Cloudflare Worker через webhook практически сразу; GitHub Actions отвечает за мониторинг Releases. Подписки и настройка перевода хранятся в Cloudflare D1, история уже доставленных релизов — в `release_state.json`. Лимит — 30 подписок.

### Последняя версия в /list

После сканирования GitHub Actions автоматически отправляет в Cloudflare Worker 3.4 список последних **опубликованных** релизов каждого успешно проверенного репозитория через защищённый `POST /catalog`. Используется время `published_at`, а не дата создания тега, поэтому учитываются стабильные версии и все Pre-release. Команда `/list` читает кэш из D1: не обращается напрямую к GitHub и работает быстро.

Отображение упрощено для мобильного Telegram: в каждой подписке показывается **жирное короткое название проекта** со ссылкой на репозиторий, на второй строке — **кликабельная версия и срок с момента публикации**, после — пустая строка. Лишние пиктограммы перед версией и временем убраны. Если два проекта разных владельцев имеют одинаковое имя, отображается полный `owner/repo`.

В каталоге помимо версии и ссылки хранится дата её публикации в UTC. При каждом вызове `/list` Worker вычисляет прошедшее время с календарной точностью: годы и месяцы, месяцы и дни, дни и часы, часы и минуты. Для совсем свежих версий показывает минуты или «только что». Числительные склоняются по-русски. Дополнительных ежеминутных записей в D1 и новых запросов GitHub ради счётчика нет. Старые записи без даты остаются читаемыми; счётчик появится при обновлении каталога.

Значения кэшируются в `settings.monitor_latest_releases`; если часть GitHub API недоступна, уже известные версии других репозиториев не пропадают. При первом подключении Worker 3.4 версия может быть неизвестна до следующей успешной проверки. Для нового проекта без опубликованных Releases показывается соответствующая отметка. Существующие уведомления, `/status`, команды и история релизов не меняются.

Требуется **отдельно развернуть** `cloudflare/worker.js` версии `3.4-clean-list` в существующем Cloudflare Worker. GitHub Actions самостоятельно Cloudflare не публикует; отдельная миграция D1 или новые секреты не нужны. До развёртывания старый Worker отвечает на `POST /catalog` кодом 404, монитор при этом продолжает работать.

## Расписание и диагностика

- **Основной планировщик:** cron-job.org вызывает GitHub Actions `workflow_dispatch` примерно **раз в минуту**.
- **Резерв:** встроенный GitHub Actions `schedule` — `4-59/5 * * * *`, примерно каждые пять минут. Встроенное расписание может задерживаться или пропускать запуски.
- **Проверка фактической работы:** [GitHub Actions — PS5 releases to Telegram](https://github.com/Vov4k957/ps5-telegram-monitor/actions/workflows/ps5-telegram.yml). Открой последний запуск и вкладку **Summary** — она показывает фактическое время, число проверенных репозиториев, отправленных уведомлений и ошибок именно текущего запуска. Сводка также показывает период паузы при rate limiting.
- **Уведомления Telegram:** новый опубликованный релиз отправляется один раз, включая Alpha/Beta/Pre-release. Изменения его описания могут обновить исходное сообщение по правилам ниже; старые релизы не пересылаются повторно.

### Умное отслеживание дополнений описаний

Бот использует **те же запросы GitHub Releases**, что и для обнаружения новых версий: дополнительной нагрузки на API нет. Для **новых** сообщений Telegram сохраняет `message_id`, чтобы позднее отредактировать именно исходное сообщение через `editMessageText`.

- Проверяются только релизы, опубликованные за последние **48 часов**.
- Для сравнения используется исходный GitHub changelog без автоматического перевода, Markdown-оформления, URL и декоративных изображений. Изменение одного лишь `updated_at` не запускает уведомление.
- Если содержание изменилось, бот ждёт **3 минуты с момента последнего замеченного содержательного изменения**. Повторная правка сбрасывает ожидание.
- После стабилизации бот тихо **обновляет прежнее сообщение**. Если появилось **минимум два новых содержательных пункта** или текст существенно расширился (не менее 300 символов и минимум на 50%), дополнительно приходит **одно короткое уведомление**. Следующие редакции того же релиза обновляют сообщение без повторных уведомлений.
- Для прежних релизов, отправленных до внедрения этой функции, создаются **только исходные контрольные записи**. Бот не пытается исправлять историю чата и не присылает уведомлений задним числом.
- Контрольные записи и незавершённые изменения сохраняются в `release_state.json` только при изменении содержимого. Если Telegram временно недоступен, попытка повторяется; если невозможно отредактировать удалённое сообщение, остальные уведомления продолжают работать.

Контрольная сумма рассчитывается по **всему очищенному описанию**, включая дополнения после 8500 символов и после первых 40 пунктов. Короткая копия текста в состоянии служит только для хранения; для оценки роста сохраняется полная длина. При первом запуске обновлённого формата контрольные записи мигрируют без уведомлений, с сохранением истории доставок и Telegram message ID.

После перевода итоговое сообщение ограничивается размером Telegram с учётом заголовка и ссылки. Сокращение закрывает блоки кода и другие HTML-теги. При явном отказе Telegram из-за разметки или длины выполняется одна попытка отправки обычного текста; сетевые ошибки не вызывают слепой повтор. Ошибки редактирования сохраняют привязку к сообщению и незавершённую правку, кроме подтверждённого отсутствия сообщения или невозможности его редактирования.

Ограничение гарантии: Telegram и запись состояния в GitHub не являются единой транзакцией. При крайне редком сбое между успешной отправкой сообщения и фиксацией состояния повторное уведомление теоретически возможно.

Важно: `last_run` и `last_heartbeat` в `release_state.json` **не означают последнюю успешную проверку**. Эти поля сохраняются только при изменении существенного состояния, чтобы не создавать до 1 440 лишних коммитов за сутки. Актуальную дату проверки смотри в **Actions → последний запуск → Summary**. Ответ Telegram `/status` подтверждает доступность Cloudflare Worker, но сам по себе не гарантирует, что GitHub Actions недавно запускался.

### Ограничения GitHub API

Монитор использует временный `GITHUB_TOKEN` из GitHub Actions и опрашивает Releases последовательно. При HTTP 500/502/503/504 или временном сбое соединения делает **не более одной быстрой повторной попытки**. При HTTP 403/429, означающем исчерпание лимита, соблюдает `Retry-After` или `X-RateLimit-Reset`; если явного срока нет, выдерживает не менее 60 секунд. Прекращает запросы к остальным репозиториям и сохраняет `github_backoff_until` в истории состояния, чтобы новый минутный запуск не возобновил обращения преждевременно. После окончания паузы монитор автоматически продолжит работу.

Релизы за период паузы будут обработаны при последующей успешной проверке, если они остаются в окне последних 30 GitHub Releases на репозиторий. При обычных проверках история не меняется — коммит не создаётся.

### Внешний планировщик

cron-job.org вызывает:

`POST https://api.github.com/repos/Vov4k957/ps5-telegram-monitor/actions/workflows/ps5-telegram.yml/dispatches`

с телом `{"ref":"main"}` и отдельным GitHub Fine-grained token, ограниченным **Actions: Read and write** только для этого репозитория. **Секреты не помещать в URL, код или сообщения Telegram.** Если токен истечёт, cron-job.org перестанет успешно запускать workflow; проверь его историю запросов и срок действия токена. Резервный GitHub `schedule` останется доступен с возможными задержками.

## Статус в Telegram через Cloudflare D1

После публикации Worker с поддержкой `POST /report`, `check_releases.py` автоматически передаёт туда итог каждого сканирования по защищённому каналу с существующим `SYNC_SECRET`. Worker сохраняет последнюю проверку в строку `settings.monitor_latest_run` Cloudflare D1 и отображает её по команде `/status`. Новую базу, таблицы или токены создавать не требуется. Новые GitHub Actions Secrets тоже не нужны.

При временной недоступности `/report` логируется предупреждение без остановки проверки релизов. В этом случае `/status` может показать устаревшую проверку и ссылку на GitHub Actions. Если Worker ещё не обновлён, новая функция Telegram пока не активна — до публикации Worker продолжит отправлять прежний ответ.

## Сохранность состояния

**Не удаляй `release_state.json`.** В нём находятся подписки, история release ID, настройки и Telegram offset. В Actions отсутствие или повреждение файла останавливает запуск без создания пустой истории.

Обработанные updates (если включён старый polling) и подтверждённые отправки сохраняются по мере выполнения. Сбой одного репозитория не мешает остальным, кроме глобального GitHub API rate limit, при котором монитор корректно приостанавливает запросы. ID отмечается доставленным только после успешного ответа Telegram; прежние ID не удаляются при выходе релиза из окна API. Workflow пытается сохранить прогресс даже после ошибки и берёт свежую `main` при запуске. При ошибке Git push сохраняет резервный артефакт на семь дней.

Абсолютное «ровно один раз» между Telegram и Git обеспечить нельзя: если Telegram принял сообщение, но ответ потерялся, либо состояние не удалось записать в Git, при повторе возможен дубль. Обычные повторные проверки и частичная ошибка после подтверждённых отправок не пересылают уже сохранённые релизы.

За одну проверку API получает до 30 последних опубликованных релизов на репозиторий. Долгий простой с большим числом новых релизов может потребовать отдельной сверки истории.

Перевод MyMemory работает без ключа; публичный changelog передаётся этому сервису. Ссылки, версии, код и известные технические термины защищены. При ошибке, исчерпании квоты или времени переводчика отправляется оригинал. Перевод не определяет, поддерживает ли релиз конкретную прошивку PS5.

## Проверки разработчика

`python3 -m unittest discover -q`

Тесты используют временные файлы и подменяют сетевые запросы. Проверяют команды и кнопки, добавление ссылкой, отсутствие старой рассылки, Alpha/Beta, перевод, сохранение истории после ошибок, отсутствие лишних коммитов, HTTP-ограничения GitHub, сводки Actions, редактирование исходных сообщений, трёхминутную стабилизацию, защиту от спама и сценарий ShadowMountPlus 1.7beta11. Реальные подписки и Telegram при тестах не меняются.

Дополнительные регрессии проверяют длинные блоки кода, лимит после перевода, резервную отправку без HTML, повтор редактирования после ошибки, полные контрольные суммы и служебные workflow с произвольным допустимым количеством подписок (0–30).

## Исходник Cloudflare Worker

Актуальный исходник хранится в [`cloudflare/worker.js`](cloudflare/worker.js), инструкция замены — в [`cloudflare/README.md`](cloudflare/README.md). Публикация Worker остаётся ручной: коммит в GitHub не заменяет код в Cloudflare.

Worker `3.1-review-fixes` атомарно предотвращает повторный захват завершённого Telegram update и превышение лимита подписок при одновременном добавлении. `/health` выполняет запрос к D1 и возвращает HTTP 503 при недоступной базе или неполных настройках. Опциональный `/check` использует тайм-аут сетевого запроса.

Тесты Worker: `node --test cloudflare/worker.test.cjs` (Node.js 24). Они выполняют реальные SQL-запросы в локальной SQLite и подменяют внешнюю сеть. Отдельный workflow запускает их при изменении Worker; минутный мониторинг по-прежнему выполняет Python-проверки.

Служебные workflow используют общую проверку структуры подписок без привязки к числу 6. `Activate Telegram Cloudflare webhook` запускается только вручную, поскольку перерегистрирует действующий webhook. Для обычной замены кода Worker повторная регистрация не нужна.
